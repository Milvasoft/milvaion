# Milvaion Helm chart

Deploys [Milvaion](https://github.com/Milvasoft/milvaion), the distributed job scheduler, on Kubernetes:

- the **API**, which also serves the dashboard, with probes on its health endpoints, a PodDisruptionBudget, an
  optional HorizontalPodAutoscaler, a ServiceAccount and a restricted security context (non-root, read-only root
  filesystem, all capabilities dropped);
- an optional **Ingress** with TLS;
- optional **built-in workers** (HTTP, SQL, Email, Command, Maintenance), each its own Deployment;
- optional **bundled PostgreSQL, RabbitMQ and Redis** for evaluation installs.

Kubernetes 1.25 or later and Helm 3.8 or later are required.

## Install

The chart is published as an OCI artifact on GitHub Container Registry.

### Evaluation install

Everything in one namespace, with the bundled dependencies:

```bash
helm install milvaion oci://ghcr.io/milvasoft/charts/milvaion \
  --namespace milvaion --create-namespace \
  --set postgresql.enabled=true \
  --set rabbitmq.enabled=true \
  --set redis.enabled=true
```

> The bundled PostgreSQL, RabbitMQ and Redis are single pods without replication, failover or backups. Use them to
> try Milvaion, not to run it.

### Production install

Point the chart at your own PostgreSQL, RabbitMQ and Redis (managed services, or operators such as CloudNativePG
and the RabbitMQ Cluster Operator) and keep their passwords in a Secret:

```bash
kubectl create namespace milvaion
kubectl -n milvaion create secret generic milvaion-external \
  --from-literal=db-password='...' \
  --from-literal=rabbitmq-password='...' \
  --from-literal=redis-password='...'
```

```yaml
# values-production.yaml
externalDatabase:
  host: postgres.internal
  username: milvaion
  existingSecret: milvaion-external
externalRabbitmq:
  host: rabbitmq.internal
  username: milvaion
  existingSecret: milvaion-external
externalRedis:
  host: redis.internal
  existingSecret: milvaion-external

ingress:
  enabled: true
  className: nginx
  hosts:
    - host: jobs.example.com
      paths:
        - path: /
          pathType: Prefix
  tls:
    - secretName: jobs-example-com-tls
      hosts: [jobs.example.com]

config:
  MilvaionConfig:
    Alerting:
      MilvaionAppUrl: https://jobs.example.com
```

```bash
helm install milvaion oci://ghcr.io/milvasoft/charts/milvaion -n milvaion -f values-production.yaml
```

The default values install no database on purpose: without `externalDatabase.host` (or `postgresql.enabled=true`)
the install stops with a message saying what to set.

Sign in as `rootuser`. The chart prints the command that reads the generated password from the Secret.

## Secrets

| Secret value | Where it comes from |
|---|---|
| JWT signing key, API key secret, root password | `auth.*`. Left empty, they are generated once and kept across upgrades (the Secret has `helm.sh/resource-policy: keep`, so an uninstall does not delete it either). Or set `auth.existingSecret` to a Secret with the keys named in `auth.secretKeys`. |
| PostgreSQL password | `externalDatabase.existingSecret` + `existingSecretPasswordKey`, or `externalDatabase.password` (stored in the chart's Secret). With `postgresql.enabled`, the bundled chart generates it. |
| RabbitMQ password | `externalRabbitmq.existingSecret` / `password`, or generated by the bundled chart. |
| Redis password | `externalRedis.existingSecret` / `password` (leave both empty for a Redis without auth), or generated by the bundled chart. |

Changing the API key secret invalidates every API key already issued. Changing the JWT key signs everyone out.

The database password is placed into the connection string with Kubernetes variable expansion, so it must not
contain `;`.

## Configuration

Anything in the API's `appsettings.json` can be set under `config`, using the same structure:

```yaml
config:
  MilvaionConfig:
    BasePath: /milvaion
    JobDispatcher:
      BatchSize: 500
    Logging:
      Seq:
        Enabled: true
        Uri: http://seq.logging:5341
```

`configFormat` picks how these reach the API:

- `env` (default): a ConfigMap of environment variables such as `MilvaionConfig__JobDispatcher__BatchSize=500`,
  loaded with `envFrom`.
- `file`: a ConfigMap mounted as `/app/appsettings.Production.json`.

Either way a change rolls the API pods. Connection settings and secrets are always set by the chart as environment
variables and win over `config`.

If you set `MilvaionConfig.BasePath`, set the Ingress path to the same prefix. The probes keep working without it.

## Database migrations

The API applies EF Core migrations and seeds the database when it starts, before it opens its port. The startup
probe gives it five minutes (`api.startupProbe.failureThreshold` x `periodSeconds`); raise that for a large
database. There is no separate migration Job, because the API has no migrate-only mode.

Install with `api.replicaCount: 1` (the default) so the first start initialises the database alone, then scale out.
On later upgrades the rolling update (`maxSurge: 1`, `maxUnavailable: 0`) starts one new pod at a time.

An init container (`api.waitForDependencies`) waits for PostgreSQL, RabbitMQ and Redis to accept connections, so
the API does not crash-loop while they start.

## Running several API pods

Several API pods share the work through Redis locks. The dashboard's live updates use SignalR without a backplane,
so a browser must stay on one pod: set `api.service.sessionAffinity: ClientIP`, and with ingress-nginx add the
annotation `nginx.ingress.kubernetes.io/affinity: cookie`. The PodDisruptionBudget is only created when more than
one API pod can run.

## Workers

Enable the built-in workers you need. Each one takes any setting from `workerDefaults` plus its own:

```yaml
workers:
  http:
    enabled: true
    replicaCount: 3
    config:
      Worker:
        MaxParallelJobs: 64
  email:
    enabled: true
    config:
      EmailConfig:
        SmtpConfigs:
          Default:
            Host: smtp.example.com
            Port: 587
            Username: milvaion@example.com
            DefaultFromEmail: milvaion@example.com
    extraEnv:
      - name: EmailConfig__SmtpConfigs__Default__Password
        valueFrom:
          secretKeyRef:
            name: smtp
            key: password
  maintenance:
    enabled: true
```

The chart sets each worker's RabbitMQ and Redis connection, turns off the Seq sink the images default to, and
stores the offline-resilience data in `/app/worker_data` (an emptyDir, or `dataVolume.existingClaim`). The
maintenance worker also gets the Milvaion database and Redis connection strings. To give another worker the database
connection string, list the variable names in `milvaionDatabaseEnv`.

Worker probes read the health files the SDK writes: `/tmp/live` (refreshed every 30 seconds) and `/tmp/ready`
(present while RabbitMQ and Redis are reachable).

The HTTP worker's chart default blocks requests to private networks (`HttpWorker.Security.BlockPrivateNetworks`);
set it to `false` if your jobs call services inside the cluster.

The command worker image (`milvasoft/milvaion-command-worker`) is not published on Docker Hub yet. Build it from
`src/Workers/CommandWorker/Dockerfile` and set `workers.command.image` until it is.

## Testing the chart

```bash
helm lint deploy/helm/milvaion --strict -f deploy/helm/milvaion/ci/bundled-values.yaml
helm template milvaion deploy/helm/milvaion -f deploy/helm/milvaion/ci/external-values.yaml
helm test milvaion -n milvaion   # after an install
```

The `ci/` values files are the cases the GitHub workflow lints and validates.

## Releasing

Bump `version` in `Chart.yaml` and push a tag `helm-v<version>`. The `Helm Chart` workflow lints the chart, pushes
it to `oci://ghcr.io/milvasoft/charts/milvaion` and attaches the package to a GitHub release.
